# Этап 1: фундамент и ядро учёта. Спецификация

- Дата: 2026-10-05
- Версия: 3.1 (ревью harness-review: раунд 1 — 13 major, раунд 2 — 5 major, раунд 3 — APPROVE; minor-замечания раунда 3 внесены)
- Статус: одобрено ревьюером, ожидает утверждения заказчика
- Референс UX: [docs/research/finmap-research.md](../../research/finmap-research.md)

## 1. Контекст и цель

Внутренний инструмент управленческого учёта для сети компьютерных клубов в Казахстане. Функционально и по UX ориентирован на Finmap (журнал операций, счета, справочники, разбиения, мультивалютность, мультикомпанейность), но с собственным брендом, текстами и кодом.

**Пользователи:** несколько доверенных людей (владелец, бухгалтер, управляющие). Все видят все данные. Ролей, публичной регистрации и биллинга нет.

**Устройства:** десктоп в приоритете. С телефона просматривают баланс и журнал, срочно вносят и правят операции.

**Развёртывание:** одна команда из терминала. Поддерживаются три режима: Windows-ПК клуба + Cloudflare Tunnel (свой домен); Windows-ПК клуба + ngrok (статический домен ngrok); VPS + Caddy.

**Название продукта:** задаётся конфигом `APP_NAME`, по умолчанию «Учёт».

### Дорожная карта (этот документ покрывает только этап 1)

| Этап | Содержание |
|---|---|
| **1** | Фундамент: запуск, вход, компании, проекты по шаблонам, справочники, операции, журнал, мультивалютность |
| 2 | Отчёты: ДДС, P&L, разрезы по проектам и статьям, дашборд, отраслевые метрики шаблонов |
| 3 | Планирование: плановые и повторяющиеся операции, платёжный календарь, план-факт |
| 4 | Импорт и интеграции: Excel/CSV, выписки банков РК (Kaspi, Halyk…), Senet, автоправила |

### Не входит в этап 1

Отчёты и дашборд, плановые и будущие операции, повторяющиеся операции, календарь, импорт, интеграции, автоправила, счета-фактуры, роли и права, AI, офлайн-режим, PostgreSQL.

## 2. Ключевые понятия

- **Компания:** юрлицо (ТОО или ИП) с базовой валютой (по умолчанию KZT). Все данные изолированы по компании.
- **Проект:** точка бизнеса внутри компании («Клуб на Ленина», «Офис»). Создаётся по **шаблону типа бизнеса**.
- **Шаблон типа бизнеса:** TypeScript-модуль в `src/templates/`. Задаёт параметры проекта, статьи, счета по умолчанию, доступные интеграции и отраслевые метрики. На этапе 1 есть два шаблона: `computer-club` и `general` («Общий», пустой).
- **Операция:** доход, расход или перевод. У операции две даты:
  - **дата оплаты** `paidAt` (момент времени): движение денег, ДДС, балансы;
  - **дата сделки** `accrualDate` (календарная дата): P&L; если не задана, равна календарной дате `paidAt`.
- **Разбиение:** доход или расход состоит из одной или нескольких строк «категория, проект, сумма». Отчёты агрегируют строки.
- **Часовой пояс приложения:** `APP_TIMEZONE` (по умолчанию `Asia/Almaty`). Используется для всех «календарных» понятий: дата операции, «сегодня», дата курса, расписание задач. Отображение тоже в этом поясе, независимо от пояса устройства.

## 3. Архитектура

Один процесс Node.js 24 LTS:

- **Сервер:** Fastify 5. Обслуживает REST API `/api/v1`, отдаёт собранную SPA и выполняет фоновые задачи по расписанию.
- **Клиент:** React 19, Vite, TypeScript, Tailwind CSS, TanStack Query, TanStack Table, React Hook Form.
- **БД:** SQLite через `better-sqlite3` (режим WAL) и Drizzle ORM (диалект sqlite), миграции Drizzle Kit. PostgreSQL не поддерживается; переход на него — отдельная будущая задача.
- **Нативные зависимости:** только пакеты с готовыми бинарниками для Windows x64 и Node 24 (`better-sqlite3`, `@node-rs/argon2`, `@ngrok/ngrok`). Visual Studio Build Tools не требуются.
- **Десятичная арифметика:** `big.js` для курсов и пересчётов. Числа с плавающей точкой для денег не используются.
- **Общий код** (`src/shared`, `src/templates`) импортируется и сервером, и клиентом: zod-схемы, работа с деньгами, шаблоны.

## 4. Модель данных

### 4.1 Общие правила

- **Идентификаторы:** целые `INTEGER PRIMARY KEY` с автоинкрементом.
- **Время:** моменты времени хранятся как UTC в ISO-8601 фиксированной ширины `YYYY-MM-DDTHH:mm:ss.sssZ` (`paidAt`, `createdAt`), чтобы лексическая сортировка совпадала с хронологической. Календарные даты хранятся как `YYYY-MM-DD` (`accrualDate`, `openedAt`, даты курсов).
- **Суммы:** целые числа в минимальных единицах валюты (`number`, безопасно до 9×10¹⁵). Количество знаков берётся из справочника валют.
- **Курсы:** десятичные строки (`TEXT`, до 10 знаков после запятой); вычисляются через `big.js`.
- **Округление** везде одно: **half-up** (половина округляется от нуля), до минимальной единицы валюты результата.
- **Распределение** суммы на части (проценты разбиения, `baseAmount` по строкам): **метод наибольшего остатка**. Каждая часть округляется вниз, затем недостающие единицы раздаются частям с наибольшими дробными остатками (при равенстве — по порядку строк). Сумма частей всегда точно равна целому.

### 4.2 Организация

- `users`: id, login (уникальный), name, passwordHash (argon2id), createdAt, disabledAt.
- `sessions`: id, tokenHash (sha-256 от случайного токена), userId, createdAt, expiresAt, lastSeenAt (обновляется не чаще раза в 5 минут), ip, userAgent.
- `user_preferences`: userId, key, value (JSON); уникальны по паре (userId, key). Хранят видимые колонки журнала, свёрнутую панель, последнюю компанию.
- `companies`: id, name, baseCurrency, archivedAt, createdAt. `baseCurrency` нельзя изменить, если в компании есть хотя бы одна операция (включая удалённые) или фиксированный курс.
- `projects`: id, companyId, name, templateKey, templateParams (JSON, валидируется схемой шаблона), orderIndex, archivedAt.

### 4.3 Валюты и курсы

- `currencies` (сид из ISO 4217): code, name, symbol, minorUnits (KZT 2, USD 2, JPY 0, KWD 3…).
- `exchange_rates`: date (`YYYY-MM-DD`), currency, rateToKzt (TEXT, курс за 1 единицу), source (`nbrk` | `manual`), createdBy (для `manual`), fetchedAt. Ключ уникален по паре (date, currency).
  - `nbrk`: значение из фида Нацбанка, делённое на `quant` (курсы публикуются за 1, 10 или 100 единиц), хранится без округления.
  - `manual`: курс к KZT, введённый пользователем **на одну конкретную дату**, чтобы закрыть пробел. Действует только на эту дату (и, как любой курс, служит запасным на 7 дней вперёд по п. 5 ниже). Если позже Нацбанк опубликует курс на эту дату, ручной **не перезаписывается**.
- `fixed_rates`: companyId, currency, rate (TEXT, за 1 единицу валюты в базовой валюте компании), validFrom (дата), validTo (дата, nullable = бессрочно). Это управленческий курс компании на период. Периоды по одной валюте не пересекаются.
- `rate_misses`: date, currency, checkedAt — отрицательный кэш: Нацбанк не вернул курс на эту дату. Повторный запрос к Нацбанку для той же пары — не раньше чем через 1 час.

**Как определяется курс** валюты X к базовой валюте B на дату D (D — дата `paidAt` в `APP_TIMEZONE`):
1. Если X = B, курс равен `1`, поиск не выполняется.
2. Если у компании есть `fixed_rates` для X, период которого (`validFrom ≤ D ≤ validTo`, где пустой `validTo` означает бессрочно) покрывает D, берётся он.
3. Иначе кросс-курс через KZT: `rate(X→KZT, D) / rate(B→KZT, D)`, где курс KZT→KZT равен 1.
4. Курс к KZT на дату D ищется в `exchange_rates` (любой источник). Если его нет и нет свежей записи в `rate_misses`, сервер запрашивает у Нацбанка фид на дату D (таймаут 5 секунд), сохраняет курсы или запись о промахе. Этот запрос выполняется **до** открытия транзакции записи (транзакции `better-sqlite3` синхронные).
5. Если и после этого курса за D нет (выходной, праздник, недоступность), берётся ближайший предыдущий, но **не старше 7 дней**.
6. Если курса нет и в пределах 7 дней, операция отклоняется с ошибкой `RATE_UNAVAILABLE`: «Нет курса {X} на {D}». В форме у ошибки есть действие «Указать курс на {D}», которое создаёт запись `manual` только на эту дату, и ссылка «Повторить».

**Точность:** кросс-курс и пересчёт выполняются в `big.js` с 20 знаками после запятой, округления на промежуточных шагах нет. В `operations.rate` для отображения сохраняется курс, округлённый half-up до 10 значащих цифр. `baseAmount` всегда считается из **неокруглённого** курса.

**Пересчёт суммы в базовую валюту:**
`baseAmount = round_half_up( amount / 10^minor(X) × rate × 10^minor(B) )`.

**В тестах и для `seed:demo`** используется источник курсов из фикстур (`RATES_SOURCE=fixtures`). Сеть в тестах не используется.

**Когда пересчитываются `rate` и `baseAmount`:** при создании операции и при изменении её `paidAt`, `amount`, `accountId` (а у перевода также `toAccountId` и `toAmount`). При правке других полей значения не меняются. Новый или изменённый фиксированный курс **не пересчитывает** уже сохранённые операции задним числом. Он применяется к операциям, которые создают или правят после этого.

### 4.4 Справочники

Все справочники привязаны к `companyId` и имеют `orderIndex` и `archivedAt`.

- `accounts`: name, currency, startingBalance, openedAt (дата), projectId (nullable).
  - `startingBalance` — остаток на начало дня `openedAt`. Операции с датой `paidAt` раньше `openedAt` запрещены. `openedAt` нельзя сдвинуть позже самой ранней операции счёта. По умолчанию `openedAt` — дата создания счёта; чтобы вносить историю, её ставят раньше.
  - `currency` нельзя изменить, если по счёту есть хотя бы одна операция (включая удалённые).
  - Баланс **не хранится**, он вычисляется (§4.7).
- `categories`: kind (`income` | `expense`), parentId (nullable; не больше 2 уровней), name, systemKey (nullable), templateRef (nullable).
  - Ключ (companyId, kind, templateRef) уникален. `templateRef` имеет префикс шаблона, например `computer-club:bar`.
  - **Системные категории** (`systemKey` не пусто) создаются вместе с компанией. Это всегда статьи верхнего уровня; их нельзя удалить, переименовать, архивировать или сделать дочерними.
    - Доходные: `investment` «Инвестиции», `loan_repaid` «Возврат займа», `credit_received` «Получение кредита».
    - Расходные: `salary` «Зарплата», `tax` «Налоги», `vat` «НДС», `dividends` «Дивиденды», `credit_repayment` «Погашение кредита», `loan_issued` «Выдача займа».
  - **Связь с типом контрагента** задаётся константой в коде по `systemKey`: salary → employee; tax и vat → tax; dividends → owner; investment → investor; credit_received и credit_repayment → creditor; loan_issued и loan_repaid → borrower.
  - **У системных категорий могут быть дочерние** (например, «Зарплата → Администраторы»). Дочерняя наследует связь родителя: её **эффективный systemKey** равен systemKey родителя. Этим этап 2 будет строить дебиторку и кредиторку.
  - **Операцию можно отнести и к родительской, и к дочерней категории.** Отчёты сворачивают дочерние категории в родителя.
- `counterparties`: type (`client` | `supplier` | `employee` | `owner` | `investor` | `creditor` | `borrower` | `tax`), name, comment.
- `tags`: name. Уникально в компании, включая архивные; при попытке создать тег с именем архивного предлагается его восстановить.
- `split_presets`: name, lines (JSON: `[{categoryId?, projectId?, bp}]`). Доля хранится целым числом в сотых долях процента (`bp`, 10000 = 100%); сумма долей должна быть ровно 10000.
- `saved_filters`: userId, companyId, name, filter (JSON).

### 4.5 Операции

- `operations`:
  - id, companyId, type (`income` | `expense` | `transfer`), status (на этапе 1 только `actual`; значение `planned` зарезервировано для этапа 3);
  - paidAt, accrualDate (nullable);
  - accountId, amount (больше 0, в валюте счёта);
  - toAccountId, toAmount (только для перевода, в валюте целевого счёта);
  - rate, baseAmount (сумма исходной стороны в базовой валюте);
  - counterpartyId (nullable), comment;
  - createdBy, createdAt, updatedAt, version (целое, оптимистичная блокировка), deletedAt.
- `operation_lines`: id, operationId, position, categoryId (nullable), projectId (nullable), amount, baseAmount.
  - У дохода и расхода не меньше одной строки.
  - У перевода либо 0 строк, либо 1 строка, если указан проект (`categoryId = NULL`).
- `operation_tags`: operationId, tagId.
- `attachments`: id, companyId, operationId, originalName, storedName, mime, size, createdAt, deletedAt. Файлы лежат в `data/uploads/`. Удаление вложения только помечает запись (`deletedAt`), физический файл на этапе 1 не удаляется. Так снимок БД и копия `uploads/` в бэкапе не могут разойтись.
- `audit_log`: id, companyId (nullable, для событий пользователей и системы), userId, entity, entityId, action (`create` | `update` | `delete` | `restore` | `archive` | `unarchive` | `reorder` | `login` | `logout` | `password_change`), diff (JSON; поля с хэшами паролей и токенами исключаются), at.

### 4.6 Инварианты

Проверяются в сервисе, в одной транзакции с записью. При нарушении возвращается 422 и код `INVARIANT_*`.

1. Если у операции есть строки, сумма `operation_lines.amount` равна `operations.amount`.
2. Сумма `operation_lines.baseAmount` равна `operations.baseAmount` (распределение методом наибольшего остатка, §4.1).
3. Категория соответствует типу операции: у дохода доходная, у расхода расходная. У перевода категории нет.
4. У перевода `accountId` и `toAccountId` различаются. Если валюты счетов одинаковы, `toAmount` равен `amount`.
5. Счёт, категория, проект, контрагент, теги и вложения принадлежат той же компании, что и операция.
6. Дата `paidAt` не позже конца текущего дня в `APP_TIMEZONE` (будущие платежи появятся на этапе 3 как плановые) и не раньше `openedAt` каждого затронутого счёта.
7. **Архив.** Цель — баланс архивного счёта всегда остаётся нулевым:
   - новый выбор архивного счёта, категории, проекта или контрагента запрещён;
   - у существующей операции, которая затрагивает архивный счёт, нельзя менять `amount`, `toAmount`, `paidAt`, `accountId`, `toAccountId`; остальные поля менять можно;
   - операцию, затрагивающую архивный счёт, нельзя **удалить**. Массовое удаление пропускает такие операции и сообщает о них как о пропущенных;
   - удалённую операцию, затрагивающую архивный счёт, нельзя восстановить, пока счёт не восстановлен из архива;
   - у архивного счёта нельзя менять `startingBalance` и `openedAt`.
8. **Архивирование:**
   - счёт можно архивировать только при нулевом балансе;
   - проект можно архивировать только когда все его счета уже в архиве;
   - компанию можно архивировать только когда все её счета уже в архиве; архивная компания скрыта из переключателя и доступна в настройках только для чтения;
   - системные категории не архивируются.
9. **Удаление справочника** (жёсткое) возможно, только если на него не ссылается **ни одна** операция, включая мягко удалённые. В остальных случаях — только архив. Мягко удалённые операции на этапе 1 хранятся бессрочно.
10. **Ссылки в JSON** (`split_presets`, `saved_filters`) не защищены внешними ключами. При применении пресета или фильтра недоступные элементы (удалённые или архивные) отбрасываются, и пользователь видит предупреждение. Пресет, в котором после этого не осталось строк, не применяется.
11. **Восстановление удалённой операции** заново проверяет инварианты 3–7 на текущем состоянии справочников и счетов (например, `openedAt` мог сдвинуться позже). Ссылки операции на архивные категорию, проект или контрагента восстановлению **не мешают**: эти ссылки уже были у операции раньше, а архив запрещает только новый выбор. Блокирует восстановление только архивный счёт (инвариант 7).
12. **Коды ошибок:** нарушение правил архива (инварианты 7 и 8) возвращает `ARCHIVED_REFERENCE`, нарушение остальных инвариантов возвращает `INVARIANT_<номер>`.
13. `account.projectId` указывает на проект той же компании. `systemKey` уникален в пределах компании и вида (`kind`).

### 4.7 Вычисления

- **Баланс счёта** = `startingBalance` + Σ поступлений − Σ списаний по операциям со `status = actual` и `deletedAt IS NULL`. Перевод уменьшает исходный счёт на `amount` и увеличивает целевой на `toAmount`. Будущих фактических операций не бывает (инвариант 6), поэтому этот баланс и есть «на сейчас».
- **Остаток после операции** считается оконной функцией по **полной** истории счёта (без учёта фильтров журнала), в порядке `(paidAt, id)`. Для строки перевода показываются остатки обоих счетов.
- **«Всего на счетах»** — сумма балансов неархивных счетов компании, пересчитанная в базовую валюту по курсу на сегодня (по тем же правилам §4.3). Если курса нет, рядом с итогом выводится предупреждение «курс {X} недоступен», а счёт в итог не включается.

## 5. Шаблоны типов бизнеса

```ts
interface BusinessTemplate<P extends z.ZodTypeAny> {
  key: string;                                   // 'computer-club'
  name: string;                                  // 'Компьютерный клуб'
  params: P;                                     // zod-схема параметров проекта
  paramsUi: { key: string; label: string; type: 'int' | 'text'; hint?: string }[];
  categories: { income: CategoryNode[]; expense: CategoryNode[] };
  // CategoryNode = { ref: string; name: string; children?: CategoryNode[] }
  //              | { underSystem: SystemKey; children: CategoryNode[] }  // дети системной статьи
  defaultAccounts: { name: string; currency?: string }[]; // '{project}' подставляется;
                                                           // валюта по умолчанию — базовая валюта компании
  integrations: string[];                        // подключаются на этапе 4
  metrics: MetricDef[];                          // объявления, расчёт на этапе 2
}
```

**Применение при создании проекта** (в одной транзакции):
1. Проверка `templateParams` схемой шаблона.
2. Слияние статей с деревом компании. Статья с тем же `(kind, templateRef)` не создаётся повторно; повторное применение ничего не меняет. Узел `underSystem` добавляет детей к соответствующей системной статье.
3. Создание счетов по умолчанию с `projectId` нового проекта и `openedAt` = сегодня.
4. Запись в `audit_log`.

Форма параметров проекта строится на клиенте из `paramsUi`, проверяется той же zod-схемой (шаблоны общие для клиента и сервера).

### Шаблон `general` («Общий»)

Без параметров, статей, счетов, интеграций и метрик. Проект по нему — просто разрез для отчётов: офис, магазин до появления своего шаблона и т.п.

### Шаблон `computer-club` («Компьютерный клуб»)

**Параметры:** `pcCount` («Количество ПК», целое, ≥ 1), `consoleCount` («Количество консолей», целое, ≥ 0, по умолчанию 0).

**Счета:** «Касса {проект}» (KZT), «Kaspi {проект}» (KZT).

**Интеграции:** `senet`.

**Статьи дохода:** выручка за смену (игровое время), бар, консоли и VIP, турниры, прочие доходы, корректировка или излишек.

**Статьи расхода:**
- под системной «Зарплата»: администраторы, премии;
- помещение: аренда, коммунальные, электроэнергия, интернет;
- оборудование: компьютерное оборудование, ремонт и обслуживание, мебель;
- ПО и подписки;
- бар: закуп бара;
- маркетинг: реклама, лояльность и бонусы за пополнение, призовые турниров;
- эксплуатация: расходники, гигиена и уборка, химчистка;
- финансы: комиссии банка и эквайринга, инкассация;
- прочее: корпоратив, благотворительность, списания.

**Метрики** (расчёт на этапе 2): выручка на ПК в день, доля бара в выручке, ФОТ к выручке, аренда к выручке.

## 6. API

Префикс `/api/v1`. Ресурсы компании вложены в `/companies/:cid/...`; объект другой компании отдаёт 404.

| Группа | Эндпоинты |
|---|---|
| Авторизация | `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`, `POST /auth/password` |
| Пользователи | `GET/POST /users`, `PATCH /users/:id` (имя, сброс пароля, отключение) |
| Настройки пользователя | `GET /preferences`, `PUT /preferences/:key` |
| Компании | `GET/POST /companies`, `PATCH /companies/:id`, `POST /companies/:id/archive` и `/unarchive`, `GET /companies/summary` (балансы для переключателя) |
| Валюты | `GET /currencies`, `GET /rates?date=&currency=`, `POST /rates/refresh` (ручной запрос к Нацбанку), `GET/POST /rates/manual`, `PATCH/DELETE /rates/manual/:id` (ручные курсы на дату; любое изменение пишется в историю действий) |
| Справочники (общий набор) | для `projects`, `accounts`, `categories`, `counterparties`, `tags`, `split-presets`: `GET/POST /companies/:cid/<res>`, `PATCH/DELETE …/:id`, `POST …/:id/archive` и `/unarchive`, `POST …/reorder` (для `categories` с перемещением, §7) |
| Фиксированные курсы | `GET/POST /companies/:cid/fixed-rates`, `PATCH/DELETE …/:id` |
| Сохранённые фильтры | `GET/POST /companies/:cid/saved-filters`, `PATCH/DELETE …/:id` (только свои) |
| Операции | `GET /companies/:cid/operations` (фильтр и курсор), `POST`, `GET/PATCH/DELETE …/:id`, `POST …/:id/restore`, `POST …/bulk` (действия `setCategory`, `setProject`, `setCounterparty`, `delete`, `restore`), `GET …/export.xlsx` |
| Балансы | `GET /companies/:cid/balances` |
| Вложения | `POST /companies/:cid/operations/:id/attachments`, `GET/DELETE /companies/:cid/attachments/:id` |
| История | `GET /companies/:cid/audit`, `GET /audit/system` (события пользователей) |
| Бэкап | `GET /backup/download` (архив §9.2; уровень всего экземпляра, доступен любому пользователю), `GET /backup/status` |

**Фильтр журнала:**
- период `from`/`to` по календарной дате `paidAt` в `APP_TIMEZONE`;
- `q`: поиск по комментарию, имени контрагента, названию счёта, названиям категорий и проектов строк; регистронезависимый, в том числе для кириллицы (§6.1);
- `amountMin`/`amountMax`: в **базовой валюте компании**, по `baseAmount`;
- `types[]`, `accountIds[]` (по исходному или целевому счёту), `counterpartyIds[]`, `tagIds[]`;
- `categoryIds[]`, `projectIds[]`: операция подходит, если **хотя бы одна строка** совпала; выбор родительской категории включает её дочерние;
- `withoutCategory`: доход или расход, у которого хотя бы у одной строки нет категории (переводы не учитываются);
- `withoutProject`: операция, у которой хотя бы у одной строки нет проекта, либо перевод без строк;
- `withoutCounterparty`: доход или расход без контрагента;
- сортировка: `date` (по `paidAt`, затем по `id`) или `amount` (по `baseAmount`), в порядке `asc` или `desc`;
- курсор и `limit` (по умолчанию 50, максимум 200).

### 6.1 Регистронезависимый поиск

SQLite умеет приводить к нижнему регистру только латиницу. Поэтому при открытии соединения регистрируется пользовательская функция `ulower(text)` (`better-sqlite3` `db.function`, реализация `toLocaleLowerCase('ru')` плюс замена «ё» на «е»). Функция регистрируется как детерминированная (`deterministic: true`). Поиск работает как `ulower(поле) LIKE '%' || ? || '%' ESCAPE '\'`, где параметр — уже приведённый к нижнему регистру запрос, в котором экранированы `\`, `%` и `_`. На объёмах этапа 1 (до сотни тысяч операций) полный перебор укладывается в бюджет §12. Если понадобится, FTS5 добавляется отдельной задачей.

### 6.2 Ошибки

Формат: `{ error: { code: string, message: string, fields?: Record<string,string> } }`.

| Код HTTP | Когда |
|---|---|
| 400 | `VALIDATION`: тело или параметры не прошли zod-схему; `fields` указывает поля |
| 401 / 403 | нет сессии / CSRF-проверка не пройдена |
| 404 | объект не найден или принадлежит другой компании |
| 409 | `VERSION_CONFLICT`: операцию изменили после загрузки |
| 422 | `INVARIANT_*` (§4.6), `RATE_UNAVAILABLE`, `CURRENCY_LOCKED`, `ARCHIVED_REFERENCE` |
| 429 | `RATE_LIMITED` |
| 500 | `INTERNAL`: детали только в логе |

## 7. Интерфейс

Собственный бренд (`APP_NAME`, своя иконка). Палитра и шрифт свои: Inter; графитовая шапка; белые карточки со скруглением; поля ввода без рамки на светло-сером фоне; зелёный для дохода и основных действий, коралловый для расхода, нейтральный серый для перевода. Цвета заданы токенами Tailwind в одном месте.

### Каркас

- **Шапка:** переключатель компаний (список юрлиц с балансами, «Добавить компанию»); кнопки «+ Доход», «− Расход», «⇄ Перевод»; история действий; меню пользователя (профиль, настройки, выход).
- **Левая панель:** «Всего на счетах» в базовой валюте; счета, сгруппированные по проектам («Общие», затем проекты по `orderIndex`), с балансами в своей валюте; «+ счёт». Клик по счёту фильтрует журнал по нему. Панель сворачивается, состояние хранится в `user_preferences`.
- **Вкладки:** «Журнал» и «Настройки». Вкладки следующих этапов не показываются.
- Текущая компания хранится в URL: `/c/:companyId/log`. Последняя открытая компания запоминается в `user_preferences`.

### Журнал

- **Тулбар:** период (все время, сегодня, вчера, текущая и прошлая неделя, текущий и прошлый месяц, текущий год, произвольно), поиск, сумма от/до (в базовой валюте), «Фильтр» (модалка с полями §6, «Готово» / «Сохранить фильтр»), сохранённые фильтры, видимые колонки (`user_preferences`), экспорт в Excel по текущему фильтру.
- **Колонки:**
  - дата (дата и время; «сегодня» и «вчера»);
  - сумма (+ зелёным, − красным, перевод нейтральным со стрелкой; если валюта счёта не базовая, вторым рядом показывается сумма в базовой валюте);
  - счёт и остаток после операции (у перевода оба счёта и оба остатка);
  - контрагент, категория, проект;
  - комментарий.
- **Разбитые операции** (больше одной строки): вместо категории и проекта показывается «N категорий» или «N проектов» с подсказкой; клик по ним открывает форму. Если включён фильтр по проекту, под суммой выводится «доля проекта: X».
- **«Указать» в пустой ячейке** контрагента, категории или проекта есть только у операций с одной строкой (для проекта — также у перевода). По клику открывается выпадающий список с поиском, значение сохраняется сразу (оптимистично, с откатом при ошибке).
- **Массовые действия** по выделенным строкам:
  - «Категория» меняет единственную строку операций с одной строкой. Пропускаются разбитые операции, переводы и операции, у которых вид не совпадает с видом выбранной категории (доходная категория к расходу);
  - «Проект» меняет единственную строку операций с одной строкой. Переводу без строк он создаёт строку. Пропускаются разбитые операции;
  - «Контрагент» применяется ко всем выделенным доходам и расходам;
  - «Удалить» с подтверждением. Пропускаются операции, затрагивающие архивный счёт. Затем тост «Удалено N — Отменить» на 10 секунд (`bulk restore`);
  - после каждого массового действия показывается итог «изменено N, пропущено M» с причинами;
  - массовые действия не проверяют `version` (последняя запись выигрывает), но увеличивают её у изменённых операций и пишут историю. Правка через «Указать» передаёт `version` и при конфликте получает 409.
- Бесконечная прокрутка, сортировка по дате и сумме. Клик по строке открывает форму.

### Форма операции (модалка; на телефоне на весь экран)

- **Доход и расход:** счёт, сумма в валюте счёта, категория, контрагент, дата оплаты (по умолчанию «сейчас»; выбрать будущий день нельзя), переключатель «Дата сделки отличается» (`accrualDate`, любая дата), свёрнутый блок «Проект, теги, комментарий, файл».
- **Перевод:** дата, со счёта, на счёт, сумма. Если валюты разные, появляются поле «Сумма зачисления» и вычисленный курс.
- **Поле суммы:**
  - принимает арифметические выражения (`+ − × /`, скобки) и вычисляет их при потере фокуса через `big.js`; результат округляется half-up до минимальной единицы валюты;
  - понимает и запятую, и точку как десятичный разделитель, пробелы игнорирует;
  - на телефоне (`inputmode="decimal"`) под полем выводится ряд кнопок `+ − × ÷`, потому что цифровая клавиатура не показывает операторы.
- **«Разделить»** включает режим строк «категория, проект, сумма или %». Индикатор показывает нераспределённый остаток; сохранить можно, только когда остаток равен 0. Проценты переводятся в суммы методом наибольшего остатка. Можно применить сохранённый шаблон разделения или сохранить текущее разбиение как шаблон.
- **Выпадающие списки** с поиском (тем же `ulower`-правилом на клиенте). Архивные элементы не предлагаются. Пункт «+ Создать „…“» создаёт контрагента, категорию, проект или тег прямо из формы. Для категории с эффективным `systemKey` список контрагентов сначала предлагает подходящий тип.
- **Кнопки:** «Сохранить» и «Сохранить и создать похожий» (форма остаётся с теми же значениями, кроме суммы, комментария и файлов).
- **Клавиши:** Enter сохраняет (вне многострочного поля), Esc закрывает; при несохранённых изменениях запрашивается подтверждение.
- **Ошибки** показываются у полей. На 409 выводится «Операция изменена другим пользователем» и кнопка «Загрузить актуальную». На `RATE_UNAVAILABLE` — текст ошибки и действия «Указать курс на {D}» (небольшая форма прямо в модалке, создаёт ручной курс) и «Повторить».
- **Режим редактирования:** есть «Удалить» и «Дублировать». Если операция затрагивает архивный счёт, поля суммы, даты оплаты и счетов заблокированы, кнопка «Удалить» неактивна; у них подсказка «счёт в архиве». Дату сделки, категорию, проект, контрагента, теги, комментарий и файлы можно менять.

### Настройки

- **Профиль:** имя, смена пароля (после смены завершаются все остальные сессии).
- **Компании:** создание, переименование, базовая валюта (заблокирована, если есть операции), архивирование.
- **Проекты:** создание по шаблону (выбор шаблона, затем форма из `paramsUi`), редактирование параметров, порядок, архивирование (§4.6, п. 8).
- **Счета:** создание, редактирование (валюта заблокирована, если есть операции), `openedAt`, стартовый баланс, порядок, архивирование (только при нулевом балансе).
- **Категории:** два дерева, перетаскивание. Правила:
  - перемещать можно только внутри своего дерева (доход или расход);
  - вложенность не больше 2 уровней;
  - категорию с дочерними нельзя сделать дочерней;
  - системные остаются на верхнем уровне и помечены значком, но в них можно вкладывать.
- **Контрагенты:** вкладки по типам, поиск.
- **Теги. Шаблоны разделения** (сумма процентов 100). **Курсы:** фиксированные курсы компании (периоды), список ручных курсов на дату (правка и удаление), текущие курсы Нацбанка и кнопка «Обновить курсы».
- **Пользователи:** список, добавление, сброс пароля, отключение. Отключение и сброс завершают сессии пользователя. Нельзя отключить себя и последнего активного пользователя.
- **Резервная копия:** «Скачать сейчас», дата последней автокопии, путь `BACKUP_COPY_DIR`.
- **История действий:** лента с фильтром по пользователю и сущности, просмотр diff.

### Мобильная версия (ширина меньше 768px)

- Журнал выводится списком карточек (сумма, категория, счёт, дата), фильтры открываются в выезжающей панели.
- Счета и «Всего на счетах» выезжают слева.
- Внизу закреплены кнопки «Доход», «Расход», «Перевод».
- Формы открываются на весь экран, у поля суммы есть ряд операторов калькулятора.
- PWA-манифест (`start_url: "/"`, относительный) и иконки, без офлайн-режима.

## 8. Безопасность и сеть

- **Пароли:** argon2id (`@node-rs/argon2`), минимум 10 символов.
- **Сессии:** кука `sid` (httpOnly, `SameSite=Lax`, `Secure`, если `PUBLIC_URL` начинается с https): 12 часов, с «запомнить меня» 30 дней, продлевается при активности. Выход, смена или сброс пароля и отключение пользователя удаляют его сессии.
- **Rate-limit:** вход — 5 неудачных попыток за 15 минут на логин и на IP (ответ 429); API — 300 запросов в минуту на сессию.
- **Адрес прослушивания:** по умолчанию `HOST=127.0.0.1`. Сервер доступен только локально, а наружу его отдаёт туннель или Caddy. `HOST=0.0.0.0` (доступ из локальной сети по HTTP) включается только явно, и тогда при старте выводится предупреждение.
- **IP клиента:**
  - Fastify `trustProxy` доверяет только loopback (`127.0.0.1`, `::1`). IP берётся как `request.ip`: `proxy-addr` идёт по `X-Forwarded-For` справа налево и останавливается на первом недоверенном адресе. Значения, которые клиент сам дописал в начало заголовка, поэтому игнорируются.
  - `CF-Connecting-IP` учитывается **только** при `DEPLOY_MODE=cloudflare` и **только** если соединение пришло с loopback (то есть от локального `cloudflared`). Cloudflare перезаписывает этот заголовок, так что подделать его через туннель нельзя. В режимах `ngrok`, `vps` и `local`, а также для соединений не с loopback (например, из локальной сети при `HOST=0.0.0.0`) он игнорируется, потому что клиент может прислать его сам и обойти rate-limit.
- **CSRF:**
  - для изменяющих запросов обязателен заголовок `X-Requested-With: fetch`. Обёртка `fetch` на клиенте добавляет его с первого шага реализации;
  - `Origin` должен входить в список разрешённых: origin `PUBLIC_URL`, `http://localhost:PORT`, `http://127.0.0.1:PORT` (доступ с самого ПК клуба во всех режимах) и значения `EXTRA_ORIGINS` (через запятую; например `http://192.168.1.10:3000` при `HOST=0.0.0.0`).
- **Заголовки:** `@fastify/helmet` с CSP для SPA.
- **Загрузки:** максимум 10 МБ. Тип проверяется по содержимому файла (`file-type`), а не по расширению. Разрешены png, jpg, webp, heic, pdf, xlsx, csv. Имя файла генерируется. Отдача только с авторизацией, с `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`.

### 8.1 Режимы развёртывания

| Режим | Как работает | Постоянный адрес |
|---|---|---|
| `local` | только `http://localhost:PORT` | — |
| `cloudflare` | `scripts/run.ts` запускает `cloudflared tunnel run` и передаёт токен через переменную окружения `TUNNEL_TOKEN` (так его не видно в списке процессов). Туннель и hostname (например `fin.example.kz → http://localhost:3000`) создаются в панели Cloudflare Zero Trust, домен должен быть в Cloudflare | да |
| `ngrok` | туннель поднимается **внутри процесса** через npm-пакет `@ngrok/ngrok` (готовые бинарники, отдельный агент ngrok не нужен) с `NGROK_AUTHTOKEN` и `domain: NGROK_DOMAIN` (бесплатный статический домен ngrok) | да |
| `vps` | Caddy как reverse-proxy с автоматическим HTTPS (`deploy/Caddyfile.example`), systemd-юнит (`deploy/finmap-clone.service`) | да |

**Откуда берётся `cloudflared`:** при выборе режима `cloudflare` `npm run setup` скачивает закреплённую версию `cloudflared` для текущей ОС с GitHub Releases в `data/bin/`, сверяет SHA-256 с зашитым в скрипт значением и использует её. Уже установленный в системе `cloudflared` используется, только если задан `CLOUDFLARED_PATH`.

**Ограничения ngrok free:** при первом открытии сайта в браузере показывается страница-предупреждение ngrok (один раз на браузер), действуют лимиты запросов и трафика бесплатного тарифа. README рекомендует `cloudflare` как основной режим для ПК клуба, а `ngrok` — когда своего домена нет.

Быстрые туннели со случайным адресом не поддерживаются: при перезапуске адрес меняется, PWA на телефоне перестаёт открываться, а вход приходится выполнять заново. `npm run setup` спрашивает режим и заполняет нужные переменные. README содержит пошаговые инструкции для каждого режима, включая получение токенов.

## 9. Надёжность и эксплуатация

### 9.1 Процесс и логи

- `scripts/run.ts` — супервизор: запускает сервер (и туннель в своих режимах), при падении перезапускает с паузой 1 → 2 → 4 … 60 секунд, пишет в лог.
- **Автозапуск** (`npm run service:install`):
  - на Windows — задача Планировщика **«при входе в систему» текущего пользователя** со скрытым окном. Она работает от имени этого пользователя, поэтому PATH, `npm` и права на папку проекта те же, что при ручном запуске. Для ПК клуба README рекомендует включить автовход в Windows. Режим «при запуске системы без входа» не поддерживается: ему нужен сохранённый пароль или учётная запись SYSTEM;
  - на Linux — systemd-юнит от отдельного пользователя.
- **Один экземпляр:** при старте сервер берёт lock-файл `data/app.lock` с PID. Если lock занят живым процессом, второй экземпляр завершается с сообщением. Lock с PID несуществующего процесса считается устаревшим и перехватывается.
- **Корректное завершение** по `SIGINT`, `SIGTERM`, `SIGHUP` (закрытие окна консоли на Windows) и `SIGBREAK`: перестать принимать запросы, дождаться активных (до 10 секунд), закрыть БД, снять lock. Если процесс убит принудительно (например, «Завершить» в Планировщике), SQLite в режиме WAL остаётся согласованной: теряются только незавершённые транзакции.
- **Логи:** pino в JSON, пишутся в `data/logs/` с ротацией (7 файлов по 10 МБ) и выводятся в консоль в читаемом виде.

### 9.2 Бэкап

- Архив `data/backups/backup-YYYYMMDD-HHmmss.zip` содержит снимок БД (`VACUUM INTO` во временный файл) и папку `uploads/`.
- **Когда создаётся:**
  - ежедневно в 04:00 (`APP_TIMEZONE`);
  - **при старте**, если последнему бэкапу больше 24 часов (ПК мог быть выключен в 04:00);
  - перед каждой миграцией;
  - вручную (`npm run backup`, кнопка в настройках).
- **Хранение:** последние `BACKUP_KEEP` архивов. Если задан `BACKUP_COPY_DIR`, каждый архив копируется и туда (с той же ротацией); ошибка копирования пишется в лог и отображается в «Резервная копия».

### 9.3 Восстановление (`npm run restore -- <архив>`)

1. Проверяет, что приложение не запущено (lock-файл `data/app.lock` с живым PID, свободный `PORT`). Иначе просит остановить: README описывает, как остановить супервизор и задачу Планировщика.
2. Проверяет версию схемы в архиве. Если она **новее** версии кода, восстановление отклоняется («обновите приложение»).
3. Переносит текущие `app.db`, `app.db-wal`, `app.db-shm` и `uploads/` в `data/pre-restore-<время>/`.
4. Распаковывает архив, проверяет БД (`PRAGMA integrity_check`), применяет недостающие миграции, **очищает таблицу `sessions`** (все входят заново).
5. Сообщает об успехе. После этого приложение запускают обычным `npm start`.

### 9.4 Курсы Нацбанка РК

- **Плановая задача:** при старте и ежедневно в 10:00 (`APP_TIMEZONE`) загружается фид на сегодня. Ошибки сети повторяются с увеличивающейся паузой (до 5 попыток), затем записываются в лог.
- **Дозагрузка по дате** выполняется по требованию (§4.3, п. 4).
- **Разбор фида** учитывает `quant`.

## 10. Тестирование

**Unit (Vitest):**
- `money.ts`: парсинг, форматирование, half-up, распределение методом наибольшего остатка (сумма частей всегда равна целому);
- калькулятор выражений (запятая, пробелы, приоритет, деление на ноль → ошибка);
- курсы: кросс-курс, `quant`, валюты с 0 и 3 знаками, правило 7 дней, курс базовой валюты = 1;
- парсер фида Нацбанка (на фикстурах);
- применение шаблонов: идемпотентность, `underSystem`, наследование эффективного `systemKey`;
- даты: граница суток в `APP_TIMEZONE` (операция в 23:30 и в 00:30 по Алматы).

**Интеграционные (Vitest и SQLite во временном файле):**
- каждый сервис: CRUD и все инварианты §4.6 (по тесту на пункт);
- мягкое удаление, восстановление, массовые действия с пропуском разбитых операций;
- архив и жёсткое удаление справочников;
- баланс и остаток после операции на смешанных операциях и переводах между валютами;
- пересчёт `rate` и `baseAmount` при правке;
- блокировка смены валют;
- изоляция компаний;
- авторизация, сессии и их отзыв, rate-limit, CSRF (разрешённые и запрещённые origin);
- определение IP: поддельный `CF-Connecting-IP` и дописанный в начало `X-Forwarded-For` в режимах `ngrok` и `vps` не влияют на rate-limit; в режиме `cloudflare` `CF-Connecting-IP` учитывается;
- инвариант 7, по тесту на каждое подправило: новый выбор архивного элемента → 422; правка суммы, даты оплаты или счетов операции на архивном счёте → 422, а правка даты сделки и комментария проходит; удаление одной операции → 422 `ARCHIVED_REFERENCE`, массовое удаление пропускает её; восстановление → 422; правка `startingBalance` или `openedAt` архивного счёта → 422; во всех случаях баланс архивного счёта остаётся нулевым;
- инвариант 11: восстановление операции с архивной категорией проходит, с архивным счётом — нет;
- курсы:
  - ручной курс на дату D действует на D (и как запасной до D+7), но не влияет на даты, для которых у Нацбанка есть курс;
  - Нацбанк не перезаписывает ручной курс;
  - фиксированный курс действует на `validFrom` и `validTo` включительно, а на `validTo + 1` уже нет;
  - пересекающиеся периоды отклоняются;
  - после промаха повторный запрос к Нацбанку не уходит раньше чем через час (часы в тесте подменяются);
- lock-файл: второй экземпляр не стартует, устаревший lock перехватывается;
- конфликт версии;
- поиск по кириллице в разных регистрах и с «ё»;
- бэкап → восстановление (round-trip, вложения на месте, WAL-файлы обработаны);
- бэкап при старте, если последний старше 24 часов.

**E2E (Playwright):**
1. Вход и выход.
2. Создание компании, затем проекта «Компьютерный клуб»: появились статьи (включая «Зарплата → Администраторы») и два счёта. Затем проект «Общий».
3. Доход, расход с разбиением на два проекта, перевод KZT → USD; балансы в левой панели и остатки в журнале верны.
4. Ширина 390px: ввод расхода с выражением через кнопки-операторы и правка операции.

**Демо-набор (`npm run seed:demo`, детерминированный):** 3 компании, 5 проектов, 8 счетов (KZT и USD), 60 категорий, 150 контрагентов, **10 000 операций за 2 года** (15% разбитых, 10% переводов).

Разработка ведётся через TDD: сначала тест сервиса или функции, затем реализация.

## 12. Критерии готовности

- **Чистый Windows-ПК** (Windows 10/11 x64, из предустановленного только Node 24 LTS, без Build Tools; `cloudflared` скачивается при setup, ngrok работает через npm-пакет): `setup.cmd`, затем `npm start` поднимает приложение. В режимах `cloudflare` и `ngrok` оно открывается с телефона по постоянному HTTPS-адресу и снова становится доступно после перезагрузки ПК (после `service:install`; при включённом автовходе Windows без участия человека, иначе после входа пользователя).
- Можно вести несколько компаний и проектов; доходы, расходы с разбиениями и переводы между валютами работают. Балансы совпадают с независимым пересчётом на демо-наборе: тестом, который сверяет SQL-баланс с суммой в JS.
- На демо-наборе (§10) и эталонной машине (4 ядра, 8 ГБ ОЗУ, SSD) первая страница журнала, применение фильтра и поиск отвечают на сервере быстрее чем за 300 мс (p95), в интерфейсе быстрее чем за 1 секунду.
- Все unit-, интеграционные и E2E-тесты проходят. `npm run backup` и `npm run restore` проходят ручную проверку по README.
