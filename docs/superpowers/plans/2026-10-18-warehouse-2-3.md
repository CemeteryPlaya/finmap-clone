# «Склад-2» и «Склад-3»: перемещение, инвентаризация, комплекты, импорт, аналитика — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans (решение владельца 2026-10-18: без субагентов — план выполняет контролёр сам, задача за задачей). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** закончить модуль «Склад» по §14 спецификации: «Склад-2» — перемещение между складами, инвентаризация, комплекты, импорт каталога и поступлений из Excel/CSV; «Склад-3» — вкладка «Аналитика» по товарам, динамика цен с подсказкой о падении маржи, списки «Мало», «Без движения», «Нет партии», выгрузка в Excel, README и приёмка с владельцем.

**Architecture:**
- **Ядро FIFO становится многоскладским.** Новая чистая функция `runStock` в `src/shared/stock-fifo.ts` проходит события ОДНОГО товара по нескольким складам сразу: поступление, взятие (продажа, списание, недостача), перемещение (взятие на складе-отправителе + партии на складе-получателе с той же стоимостью) и излишек (партия по цене последней партии склада). Прежний `runFifo` остаётся обёрткой над ней — его тесты становятся тестами равенства.
- **Единица пересчёта — «группа»:** товар и множество складов, замкнутое по перемещениям этого товара (`transferClosure`). Без перемещений группа — прежняя пара (склад, товар), поэтому скорость клубов без перемещений не меняется. Загрузка событий, пересчёт с записью партий и остатки на дату (`GET balance`) идут через один загрузчик `loadGroupEvents` — расхождения между ними невозможны.
- **Комплект** своего остатка не имеет: строка продажи комплекта даёт события взятия в парах его составляющих (`stock_allocations.component_item_id`). Себестоимость строки комплекта — сумма взятого.
- **Инвентаризация** — документ-черновик, который не влияет на FIFO; «Провести» фиксирует `expected_qty` (остаток на момент документа), разница становится недостачей (взятие) или излишком (партия).
- **Импорт** без кэша: файл отправляется дважды — для проверки (`commit=0`) и для записи (`commit=1`); запись перепроверяет всё и пишет одной транзакцией с одним пересчётом затронутых групп.
- **Аналитика** читает производные таблицы (`stock_allocations`, `stock_batches`) и строки документов; стоимость склада на дату — через `GET balance` с датой.

**Tech Stack:** Node 24, TypeScript, Fastify 5, zod 4, Drizzle + better-sqlite3, React 19, TanStack Query 5, Tailwind 4, Vitest (node), Playwright. Новых пакетов нет.

**Spec:** [docs/superpowers/specs/2026-10-15-warehouse-design.md](../specs/2026-10-15-warehouse-design.md): §2, §3 (схема уже есть — миграция 0007), §5.2 (перемещение, инвентаризация, комплект), §5.3, §7, §8, §9.1, §10, §11, §13, §14; блок «Решения планирования плана Склад-1» (решения 1–18 действуют и здесь).

## Решения, принятые при планировании

Все решения ниже — уточнения спецификации; в последней задаче они переносятся в спецификацию блоком «Решения планирования планов Склад-2 и Склад-3».

1. **Без схемы.** Миграция 0007 уже содержит `to_warehouse_id`, `counted_qty`, `expected_qty`, `status`, `source`, `source_ref`, `stock_combo_parts`, `stock_allocations.component_item_id`, `stock_batches.source_batch_id`. Новой миграции нет. Если задаче понадобится индекс — это отдельная миграция 0011 через `drizzle-kit`, с записью решения в задаче.
2. **Типы документов.** `STOCK_DOC_TYPES` = `receipt | sale | writeoff | transfer | count`. Подписи: «Перемещение», «Инвентаризация»; буквы номера: «М», «И» (`М-0001`, `И-0001`, кириллица).
3. **Перемещение.** `warehouseId` — отправитель, `toWarehouseId` — получатель (только у перемещения; у других типов — 400 «Склад-получатель — только у перемещения»). Тот же склад — 422 `VALIDATION` «Склад-получатель совпадает с отправителем» у поля `toWarehouseId`. Архивный получатель — как архивный склад (`ARCHIVED_REFERENCE`, кроме уже выбранного). Строки без суммы (как у списания), контрагента и причины нет. Перемещение требует остатка всегда, как ручное списание: непокрытое количество после любого пересчёта — 422 `INSUFFICIENT_STOCK` с прежним текстом по складу-отправителю. На складе-получателе каждое взятие из партии создаёт свою партию: та же стоимость и количество, `at` перемещения, `origin_line_id` — строка перемещения, `source_batch_id` — исходная партия.
4. **Группа пересчёта.** `transferClosure(ex, itemId, warehouseIds)` — наименьшее множество складов, содержащее данные и замкнутое по проведённым неудалённым перемещениям этого товара (в обе стороны). Пересчёт документа: группы считаются ДО изменения строк по объединению старых и новых пар документа (новое перемещение добавляет обе стороны в исходное множество — этого достаточно, чтобы покрыть и старую, и новую группу). Очистка и построение — по группам. `GET balance?warehouse=W` симулирует замыкание `{W}` по перемещениям ВСЕХ товаров (`transferClosure` без товара) и показывает только склад `W`.
5. **Комплект.** Признак `isCombo` задаётся только при создании товара (`PATCH` его не меняет). Единица комплекта — «шт» или «уп» (иначе 422 `VALIDATION` у поля `unit`: «Комплект считается в штуках или упаковках»). Состав — 1–20 составляющих, без повторов, не комплект («Комплект не может входить в другой комплект»), не сам комплект, из этой компании, количество по правилу единицы составляющей (`qtyError`). Состав меняется (`PATCH items/:id` с `parts`), только пока по комплекту нет неудалённых документов: иначе 422 `INVARIANT_9` «По комплекту есть документы — состав изменить нельзя» (решение: история себестоимости не переписывается задним числом; новый состав — новый комплект). Комплект разрешён только в продаже: в поступлении — 422 `VALIDATION` «Комплект нельзя оприходовать — оприходуйте его составляющие» (§10), в списании, перемещении и инвентаризации — «Комплект — только в продаже: используйте его составляющие». Количество составляющей в продаже = `line.qty × part.qty / 1000` (целое: `line.qty` кратно 1000). В «Остатках» комплектов нет; в каталоге — пометка «Комплект» и состав.
6. **Инвентаризация.**
   - Создание: `POST docs` с `type: 'count'`, `at`, `warehouseId`, `lines` (может быть пустым) и необязательным `fill: true` — тогда сервер добавляет строки для всех некомплектов с ненулевым остатком склада на момент `at` (по возрастанию `name_key`), кроме уже переданных. Документ создаётся черновиком (`status: 'draft'`), строки — `{itemId, countedQty: number | null}`, `qty = 0`, `expected_qty = null`. Черновик в FIFO не участвует.
   - Ответ документа-инвентаризации несёт у каждой строки `expected` — у черновика остаток на момент `at` прямо сейчас, у проведённой — `expected_qty`.
   - Правка черновика: `PATCH docs/:id` с `version`, `at?`, `comment?`, `lines?` (склад не меняется: 422 `VALIDATION` у поля `warehouseId`). Правка и удаление черновика историю пишут, пересчёта нет.
   - Проведение: `POST docs/:id/post` с `{version}`. Каждая строка должна иметь `countedQty` (иначе 422 `VALIDATION` с полем `lines.{i}.countedQty` «Внесите факт или удалите строку»); пустой документ — 422 «Добавьте хотя бы одну строку». В одной транзакции: `expected_qty` = остаток на момент документа без него самого (`qtyAt`), `qty = |counted − expected|`, `status = 'posted'`, версия +1, пересчёт групп строк. Недостача — взятие с обязательным остатком (как списание: после пересчёта непокрытое — 422 `INSUFFICIENT_STOCK`); излишек — партия по цене последней партии товара на этом складе до момента документа: `floor(costIn × q / qtyIn)` последней по порядку партии; партий не было — стоимость 0 и признак `unknownCost` («цена неизвестна»).
   - Ответ проведённой инвентаризации несёт `countSummary: {shortage: number, surplus: number, unknownCost: number}` — деньги недостачи (сумма взятого), излишка (сумма партий) и число строк излишка без цены. Клиент показывает «Недостача на X ₸, излишек на Y ₸».
   - Проведённую инвентаризацию изменить нельзя: `PATCH` — 422 `VALIDATION` «Проведённую инвентаризацию изменить нельзя — удалите её и проведите заново». Удаление — как у других документов, с `dryRun`.
   - Дата не в будущем (`INVARIANT_6`), как у всех документов.
7. **Остаток на момент** (`qtyAt`) — сумма количеств событий склада строго раньше момента документа в порядке `(at, docId, position)`: поступление и излишек `+`, продажа, списание, недостача `−`, перемещение `−` у отправителя и `+` у получателя. Непокрытое не вычитается отдельно — это и есть «остаток с учётом проданного без партии», как в «Остатках».
8. **Номер черновика** выдаётся при создании, как у других документов (`И-0001`), и не освобождается.
9. **Импорт** (`§9.1`).
   - `POST stock/import/items?commit=0|1` и `POST stock/import/receipts?warehouse=ID&commit=0|1`; тело — байты файла (`application/octet-stream`), имя — заголовок `x-file-name`, как у импорта журнала; не больше 5 МБ (`STOCK_IMPORT_MAX_BYTES`), не больше 5 000 строк данных (`STOCK_IMPORT_MAX_ROWS`). Читатель — `readImportFile` из `modules/imports/read-file.ts`.
   - Первая непустая строка — заголовок; имена столбцов без учёта регистра и пробелов по краям. Каталог: «Название» (обязательно), «Группа», «Единица» (`шт`, `л`, `кг`, `уп`; пусто — `шт`), «Штрихкод», «Цена продажи». Поступления: «Дата» (обязательно; дата или дата и время, без времени — 12:00 по `APP_TIMEZONE`), «Поставщик», «Товар» (обязательно), «Количество» (обязательно), «Сумма» или «Цена» (одна из двух обязательна; обе — берётся «Сумма»).
   - Ответ проверки: `{rows, errors: [{row, field, message}] (не больше 100, плюс `errorsTotal`), create: {items, groups, suppliers}, skip: {items}, docs, lines, total}`; запись — тот же ответ плюс `committed: true`; при ошибках запись — 422 `IMPORT_INVALID` с ответом проверки в `details`.
   - Каталог: товар с тем же `name_key` уже есть — строка пропускается («Уже есть»), не обновляется. Дубль названия внутри файла — ошибка строки. Цена продажи больше нуля — первая строка истории с сегодняшней даты.
   - Поступления: строки с одинаковыми моментом и поставщиком — один документ «Поступление» (строки в порядке файла, не больше 200 — иначе следующий документ). Неизвестный товар создаётся с единицей «шт» (дробное количество у него — ошибка строки «Количество в штуках — целое»); неизвестный поставщик — контрагент типа «Поставщик». Комплект в строке — ошибка строки (решение 5). Дата в будущем — ошибка строки. `source = 'import'`, `source_ref` = первые 16 символов hex SHA-256 файла + `:` + номер первой строки документа; повторная загрузка того же файла — ошибка проверки «Этот файл уже загружен».
   - Запись — одна транзакция `BEGIN IMMEDIATE`: справочники, документы и строки, затем один пересчёт всех затронутых групп; история — одна запись `stock_import` с числами (без названий).
10. **Аналитика** (`§8`).
    - `GET stock/analytics/items?from&to&warehouse?` → `{rows, totals}`. Строка на товар с движением за период (продажи, списания, недостачи, излишки или поступления): `soldQty`, `revenue` (сумма строк продаж), `cost` (себестоимость продаж — сумма `stock_allocations.cost` строк продаж), `profit = revenue − cost`, `marginBp = round(profit × 10000 / revenue)` (null при нулевой выручке), `lossCost` (списания + недостачи инвентаризаций), `lossQty`, `avgSalePrice = round(revenue × 1000 / soldQty)`, `avgPurchasePrice = round(Σ amount поступлений × 1000 / Σ qty поступлений)` за период (null без поступлений), `noBatchQty` (непокрытое в продажах). Комплект — своей строкой (выручка и себестоимость его строк); у составляющих — только их собственные продажи. Период — по дате документа (`at`) по `APP_TIMEZONE`, как журнал. Без склада — все склады компании (архивные тоже).
    - `totals`: `revenue`, `cost`, `profit`, `losses`, `surplus` (излишки инвентаризаций), `purchased` (сумма поступлений за период), `valueStart` (стоимость на конец дня перед `from`), `valueEnd` (на конец дня `to`), `valueChange = valueEnd − valueStart`. Строка §6.2 на экране: «Закуплено за период X, стоимость склада изменилась на Y».
    - `GET stock/analytics/lists?warehouse?&days=30` → `{low, stale, noBatch}`: «Мало» — как в «Остатках»; «Без движения» — товары с остатком > 0, у которых последняя продажа (или поступление, если продаж не было) раньше, чем `days` дней назад (`days` 1–365, по умолчанию 30); «Нет партии» — товары с непокрытым количеством продаж: количество и самая ранняя дата.
    - `GET stock/analytics/prices/:itemId?from&to&warehouse?` → `{purchases: [{at, docId, docNumber, unitCost}], salePrices: [{validFrom, price}], margins: [{at, marginBp}], hint: string | null}`. `unitCost = round(amount × 1000 / qty)`. Цена продажи — вся история, ступенями. Маржа считается в каждой точке закупки и каждой смене цены: `(цена − последняя закупка на эту дату) / цена`. Подсказка — если последняя закупка (по всей истории до `to`) дороже предыдущей, а цена продажи на дату предыдущей закупки равна текущей цене (сравниваются значения, а не строки истории: запись той же цены другой датой ценой не считается): «Закупка выросла на N% с {ДД.ММ.ГГГГ}, маржа упала до M%» (N — целые проценты роста, дата — последней закупки, M — маржа текущей цены к последней закупке, целые проценты). У комплекта закупок нет — подсказки нет, `purchases` пуст.
    - `GET stock/analytics/export.xlsx?from&to&warehouse?` — лист «Товары» (колонки таблицы + строка «Итого») и лист «Итоги»; писатель `src/server/http/xlsx.ts`, имя файла — `export-name.ts`.
11. **Клиент.**
    - «Документы»: кнопки «+ Перемещение» и «+ Инвентаризация»; в списке у перемещения «Склад → Склад», у инвентаризации «Черновик» или «Проведена»; сумма у обоих — «—».
    - Форма перемещения — та же `DocForm`: шапка «Откуда» (склад) и «Куда» (склад-получатель), строки «товар — количество».
    - Инвентаризация — своё окно `CountForm` на `Modal`: таблица «Товар — Учёт — Факт — Разница», «+ Добавить товар», «Сохранить черновик», «Провести» (с вопросом «Провести инвентаризацию? Остатки изменятся»), после проведения — итог «Недостача на X ₸, излишек на Y ₸» и только чтение.
    - «Товары»: в `ItemEditor` флажок «Комплект» (только при создании) и состав «товар — количество»; у комплекта с документами состав только для чтения с подсказкой.
    - Импорт — окно `StockImportDialog`: «Товары» → «Импорт из Excel», «Документы» → «Импорт поступлений» (со складом из адреса). Шаги: выбор файла → проверка (числа, «Будет создано», до 100 ошибок со строками) → «Загрузить» (неактивна при ошибках) → итог.
    - «Аналитика» — четвёртая подвкладка (`/c/:id/stock/analytics?warehouse=&period=…`), склад — «Все склады» или один. Период — те же значения и разбор адреса, что у отчётов (`parseReportSearch`, `reportRange`). Таблица по группам с итогами, плашка итогов со строкой §6.2, три списка, кнопка «Excel». Щелчок по товару — окно «Динамика цен» с графиком SVG (`lib/charts.ts`: точки закупки, ступенчатая линия цены продажи) и таблицей точек, подсказка §8 сверху.
12. **Скорость.** Пересчёт группы — полный проход, как в Склад-1 (решение 2). Новый сценарий `bench:reports` не нужен; в задаче 5 тест-замер: импорт 5 000 строк поступлений в пустую компанию укладывается в 10 с на машине разработки (`it(..., 30_000)` с проверкой времени).

## Решения по ревью плана (harness-review, manual-pass, 2026-10-18: REQUEST_CHANGES, 4 major, 12 minor)

- **R1 (M1, CSV склада).** Читатель CSV узнаёт заголовки журнала, поэтому файл склада в cp1251 даёт F8, а CSV через «,» читается одной колонкой. Задача 5 меняет общий читатель: `readCsv(data, headers?: CsvHeaders)` и `readImportFile(data, name, headers?: CsvHeaders)`, где `interface CsvHeaders { count(values: string[]): number; isHeader(values: string[]): boolean }`. По умолчанию — прежние `countKnownHeaders` и `isHeaderRow` журнала, поведение журнала не меняется (тест: прежние `import-csv.test.ts` зелёные плюс новый тест на CSV склада через «,» и в cp1251). Файлы задачи 5 — ещё `src/server/modules/imports/csv.ts` и `read-file.ts`. Предел строк читателя (50 010, 400 F5) срабатывает раньше предела склада только у файлов больше 50 010 строк; 5 001–50 010 строк — 422 склада.
- **R2 (M2, строка комплекта).** «Непокрытое» любой строки взятия — сумма `qty` списаний строки с пустой партией (`batch_id IS NULL`), а не `l.qty − покрытое`: у обычной строки это одно и то же, у строки комплекта считается в единицах составляющих. Так считают `dtoOf` (`docs.ts`), `storedSigs` (`recalc.ts`) и `value()` (`balance.ts` — меняется в задаче 3, вопреки прежнему «без изменений»).
