## Отложено (не блокирует)

1. **Правка операции из формы, которая шлёт все поля (шаг 6).**
   - `toAccountId` и `toAmount` в схеме правки не принимают `null`: `{ toAccountId: null }` у дохода даёт 400.
   - У перевода в одной валюте новая сумма вместе со старой суммой зачисления даёт `INVARIANT_4`.
   - Форма шага 6 должна отправлять только изменённые поля, либо схему нужно смягчить.
2. **Строки операции пересоздаются при каждой правке** (новые id). Сейчас безвредно; станет важно, если что-то начнёт ссылаться на id строк.
3. **Проверки инвариантов идут до транзакции записи.** Сервис синхронный, поэтому это безопасно; UPDATE уже проверяет версию в SQL. Когда появится асинхронная загрузка курсов Нацбанка, проверки нужно перенести внутрь `mutate`.
4. **Нет теста исключения запланированных операций (`status = 'planned'`) из баланса.** Через API их пока не создать — тест появится вместе с плановыми операциями (этап 3).
5. **Устаревшие комментарии** в заглушках `createReferencesService` и `createBalancesService` («до шага 4 … заглушка»): заглушки оставлены как значения по умолчанию для модульных тестов.
6. **Производительность при росте:**
   - `accountBalance` — два агрегатных запроса на счёт;
   - `/companies/summary` — расчёт по каждой компании;
   - списки в плане 4b считают флаги по строкам.
   При текущих объёмах это неважно; пересмотреть на замерах шага 5 (демо-набор 10 000 операций).
7. **`allocate` допускает нулевые веса**, если сумма весов положительна (такой вес получает 0).
8. **Если нет курса ни валюты, ни базовой валюты**, в `unavailable` попадает только валюта счёта: `resolve` проверяет её первой.
9. **Нет проверки на целое без потери точности** для суммы «Всего на счетах» и результата `convertMinor`. На реальных данных это теоретический риск.
