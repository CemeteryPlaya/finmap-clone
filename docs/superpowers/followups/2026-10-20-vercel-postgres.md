# Vercel + Postgres: итоги и что осталось

План: [2026-10-20-vercel-postgres.md](../plans/2026-10-20-vercel-postgres.md). Ветка `stage1/plan1-skeleton`, коммиты `3641a6b..5f1cbb3`.

## Что сделано

- **Код работает с двумя базами.** Локально, как раньше, используется файл SQLite. На Vercel используется Postgres (Neon). Весь слой данных переведён на async. Схема Postgres строится из схемы SQLite, поэтому имена совпадают; это проверяет тест паритета. Миграции Postgres лежат в `src/server/db/migrations-pg`.
- **Все серверные тесты идут на обеих базах.** Проекты vitest: `unit`, `server-sqlite`, `server-pg` (PGlite). e2e на Postgres запускается командой `E2E_DB=pg npx playwright test`.
- **Режим `vercel`.**
  - Точка входа `src/server/vercel-entry.ts` собирается в `server.mjs`.
  - Конфиг лежит в `vercel.json`: регион fra1, сборка с миграциями, ежедневное задание.
  - IP клиента берётся из `X-Forwarded-For`.
  - Интерфейс отдаёт сама функция: для Fastify Vercel не раздаёт статику с CDN.
- **Файлы через Vercel Blob.**
  - Вложения и файлы импорта браузер грузит прямо в приватное хранилище.
  - Скачивание вложения идёт по подписанной ссылке, она действует 5 минут.
  - Выгрузки Excel больше 4 МБ сохраняются в хранилище и скачиваются по ссылке.
  - Проверка импорта переживает переход на другой экземпляр функции.
- **Бэкапы.**
  - Ежедневное задание `GET /api/v1/cron/daily` выгружает базу в `backups/<дата>.json.gz` и хранит 14 последних копий.
  - Оно же чистит загрузки и выгрузки старше суток и удаляет истёкшие сеансы.
  - Восстановление: `npm run restore -- --pg <файл> [--force]`.
- **Перенос данных.** Команда `npm run db:to-pg -- --from <копия app.db> --to <postgres://…> [--files]` переносит все таблицы одной транзакцией и печатает сверку.
- **Пользователи.** `npm run user:add` и `user:passwd` работают и с Postgres, если задан `DATABASE_URL`.
- **README.** Добавлен раздел «`vercel` — Vercel и Neon, без своего компьютера».

## Что осталось: запуск (задача 18, нужен аккаунт владельца)

Шаги и команды описаны в README, в разделе «`vercel`». Порядок такой:

1. `vercel login`, `vercel link`. Затем подключить Neon (Frankfurt) и Blob (Private), задать `SESSION_SECRET` и `CRON_SECRET`.
2. `vercel env pull .env.vercel.local`. Затем запустить `db:to-pg` с `--files`: сначала на ветке Neon для Preview, потом на основной. Итог сверки должен быть «Совпадает».
3. `vercel --prod`. После этого проверить:
   - вход;
   - журнал и поиск «ё»;
   - импорт настоящего файла;
   - вложение на 8 МБ;
   - выгрузку Excel;
   - все вкладки «Аналитики»;
   - склад: приход, списание, инвентаризацию;
   - работу с телефона;
   - на следующее утро — что бэкап появился в Blob.
4. Замеры на ветке Neon (база должна быть пустой): `npm run bench:reports -- --pg <адрес>`, `bench:journal -- --pg`, `bench:import -- --pg`.

Что проверится только на настоящих Neon и Vercel:

- `lower()` для кириллицы при локали базы Neon;
- блокировка записи при нескольких соединениях;
- скорость массовых действий через сеть: на PGlite 500 операций занимают 6,5–9,7 с, потому что запрос идёт на каждую операцию. Если на Neon будет заметно медленнее, их нужно переписать на пакетные запросы;
- бинарный модуль `@node-rs/argon2` под linux-x64;
- p95 отчётов. Цель — меньше 1 с на «5 лет истории».

## Отложено

- В Postgres выгрузка базы идёт в режиме READ COMMITTED. Если во время выгрузки в 04:00 идёт запись, снимок будет не вполне согласованным. Исправление — режим REPEATABLE READ.
- `restore --pg` восстанавливает и таблицу сеансов, поэтому фраза «все пользователи войдут заново» для `--pg` неверна.
- Импорт склада (каталог, поступления) по-прежнему передаёт файл телом запроса. Файл больше 4,5 МБ на Vercel не загрузится.
- `db:to-pg --files` берёт вложения из папки `uploads` рядом с копией базы. Если скопировать только `app.db`, вложения не переедут.
- `db.query.*` (реляционный API Drizzle) обходит очередь соединения SQLite. Сейчас он не используется, но его стоит добавить в запреты теста `no-sync-db`.
- `attachDatabasePool` из `@vercel/functions` для Fluid compute не подключён.
- better-sqlite3 остаётся: переход на libsql отменён после замера (локально libsql синхронный, пул зависает). Строка 26 в Plans.md всё ещё называется «libsql вместо better-sqlite3».
- Ключ загруженного файла принимается от клиента. Защиты уже есть:
  - строгий шаблон `uploads/<вид>/<uuid>`;
  - проверка, что файл существует;
  - проверка содержимого и размера;
  - после прикрепления файл переносится под новый ключ.

  Остаётся одна возможность: другой вошедший пользователь может прикрепить чужую ещё не прикреплённую загрузку, но только если знает её случайный UUID. Чтобы закрыть и её, нужно добавить id пользователя в ключ (`uploads/<вид>/<userId>/<uuid>`) и проверять его при прикреплении.
