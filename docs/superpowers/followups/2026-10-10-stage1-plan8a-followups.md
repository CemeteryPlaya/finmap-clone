# Этап 1, план 8a (режим vps, автозапуск, остановка, копии бэкапов, README): итоги и отложенные замечания

**Ветка:** `stage1/plan1-skeleton`, коммиты e9fddd1..103aaa2: 7 задач, доработки в задачах 2–5 и 7, волна финальных правок 5812534 и остаточные правки 103aaa2.

## Что сделано
- **Режим `vps`.** Caddyfile и systemd-юнит с песочницей строятся из настроек, примеры лежат в `deploy/`. Режим требует `PUBLIC_URL` вида `https://домен`.
- **Блокировки.** Состояния `free` / `held` / `suspect`. Блокировка супервизора атомарная: файл появляется сразу с содержимым и снимается по `token`. Процесс по PID из блокировки проверяется по образу: чужая программа с тем же PID приложением не считается.
- **Супервизор.** Пишет журнал `data/logs/supervisor.log`. В журнал попадают:
  - ошибки настроек и сборки;
  - ошибки чтения файла настроек;
  - stderr сервера построчно, с декодером UTF-8;
  - сбой самого супервизора.

  Ещё супервизор забирает заявку на остановку и ведёт журнал cloudflared.
- **`npm run stop`.**
  - Сначала мягкая остановка через заявку; через 20 с — принудительная, с проверкой, что процессов не осталось.
  - Ожидание считается по монотонным часам.
  - Работает и при сломанных настройках.
  - Не завершает процесс, который не удалось опознать как приложение (итог `foreign`).
- **Автозапуск.** `npm run service:install` / `service:uninstall`, с `--dry-run`.
  - Windows: задача Планировщика из XML при входе пользователя, без окна (`conhost --headless`).
  - Linux: файлы в `data/deploy/` и подсказка с командами `sudo`; сам `sudo` не вызывается.
- **`BACKUP_COPY_DIR`.** Папка копий не создаётся сама: если флешка отключена, копия не уходит на системный диск.
- **README для владельца клуба.** Описывает установку в профиль пользователя, режимы, автозапуск, остановку, бэкапы, восстановление, обновление и неполадки. Команды для VPS выполняются от пользователя приложения. Раздел «На телефоне — как приложение» сохранён.

## Отложено (не блокирует)
1. **PID чужого процесса node.** Если PID из блокировки достался другому процессу node, он всё ещё считается приложением. Нужен признак жизни, не зависящий от PID (именованный канал или сокет).
2. **Гонка трёх одновременных запусков** при устаревшей блокировке супервизора. Вторым рубежом служат `app.lock` сервера и порт.
3. **Остатки после сбоя и мелочи блокировки:**
   - после сбоя может остаться `<lock>.<token>.tmp`;
   - сообщение «PID 0» для свежего нечитаемого lock;
   - запасной путь записи через `wx` (FAT/exFAT) без отдельного теста.
4. **Журналы:**
   - `cloudflared.log` не ротируется;
   - хвост stderr без перевода строки может потеряться при остановке;
   - очень длинная строка stderr делится на части.
5. **Сбои, которые не доходят до `supervisor.log`:**
   - ошибки до старта `run.ts` (сломанные `node_modules`, перенесённый Node);
   - сбой супервизора во время уже начатой штатной остановки оставляет код выхода 0;
   - у обработчика сбоя (F4) нет теста.
6. **`service:*`:**
   - сбой запуска `schtasks /Query` выдаётся как «задача не найдена»;
   - сообщение об ошибке идёт в stdout, при сигнале выводится «код null»;
   - другие менеджеры пакетов (yarn/pnpm) не различаются;
   - управляющие символы в путях XML не отсекаются.
7. **Linux вне systemd:** после принудительной остановки остаётся cloudflared.
8. **Мелочи vps-режима и бэкапов:**
   - `PUBLIC_URL` с частным IP / IPv6 / `*.localhost` принимается;
   - userinfo и путь в `PUBLIC_URL` попадают в комментарий Caddyfile;
   - `backup.ts` завершается с кодом 0 после сбоя копии (так по плану);
   - `restoreAllMocks` без `finally` в тесте бэкапа.
